# v1.2.3 — UTC timestamps and DST-safe monitoring

Fixes the autumn clock rollback causing fresh meter readings to be reported as
being in the future (issue #47).

- Store new SQLite and JSON measurement timestamps in canonical UTC with an
  explicit offset. Containers and internal logging use UTC.
- Keep dashboard presentation, daily filenames and daily/monthly/yearly
  statistics in Europe/Berlin, including 23- and 25-hour local days.
- Calculate monitoring and health-check ages in UTC using the latest inserted
  measurement. Keep existing alarm thresholds.
- Introduce database schema 3 and an explicit migration tool with read-only
  preview, consistent snapshot, documented source-timezone ranges for mixed historical
  data, per-row DST fold decisions, original-timestamp
  audit, integrity checks and protection against overwriting existing backups.
- Preserve UTC offsets when importing archived JSON and roll back the complete
  import if any entry is invalid.
- Retain the directory mount needed for SQLite WAL access, read-only backend
  access, restart policies, and 128/256 MiB reader/backend memory limits.

**Upgrade requires migration before starting the new containers against existing
measurements.** Do not simply pull `latest` against a schema-2 database. See
[UTC migration and rollback instructions](../utc-migration.md).

Tests cover DST rollback, 23/25-hour days, Berlin calendar boundaries, timestamp
normalization, migration safety, schema guards and atomic JSON import.
